# 一方修改，另一方移动：冲突行为与需求

本文补充 [requirement.md](requirement.md) 的严格合并需求，描述函数被移动到其他文件或位置时的行为。以下增强能力为目标需求，尚未实现。

**确定的规则：一方修改函数，另一方移动同一函数，必须产生冲突。** 即使识别到了移动关系，或 Git 能自动把修改应用到目标位置，也不能直接视为合并成功。

**期望的增强：尽可能识别移动后的函数位置，把“修改与删除”解释为“修改与移动”，并提供关联位置、匹配依据和双方变化，帮助人决定如何处理。** 无法确定时明确写“疑似移动”，保留原有冲突。

## 1. Git 通常会发生什么

base 中，`old.ts` 包含：

```typescript
export function target() {
  return 1;
}

export function stay() {
  return 0;
}
```

change A 将 `target()` 的返回值改为 `2`，位置不变。

change B 从 `old.ts` 删除 `target()`，保留 `stay()`，并在 `new.ts` 中放入原函数：

```typescript
export function target() {
  return 1;
}
```

Git 的 rename 检测主要针对文件，不是函数。原文件仍然存在、只有一个函数被移走时，即使开启文件 rename 检测，也不能据此保证 Git 会识别函数移动。

此前用 Git 2.53.0 在 change A 上合并 change B，并通过 `-Xno-renames` 关闭 rename 检测，得到：

```text
UU old.ts
A  new.ts
```

原文件发生内容冲突，从实体角度看是一方修改、一方删除。用 diff3 展示为：

```text
<<<<<<< ours：change A
export function target() {
  return 2;
}

||||||| base
export function target() {
  return 1;
}

=======
>>>>>>> theirs：change B
export function stay() {
  return 0;
}
```

`new.ts` 则正常加入，里面的 `target()` 仍返回 `1`，没有自动获得 A 的修改。

此时只处理原文件的冲突，容易遗漏两文件之间的关系：接受删除可能遗漏 A 的改动；保留旧位置的函数可能留下两份定义。最终正确结果需要人结合移动目的和函数变化判断。

这不是所有移动场景的固定输出。如果整个原文件被删除，Git 可能报告文件级 modify/delete；若识别到整个文件的 rename，可能沿新路径合并修改。两种情况都必须遵守本项目的严格规则，不能依赖 Git 恰好产生哪种冲突。

## 2. 希望得到的冲突信息

建议将两处变化关联为一个待审核事项。例如：

```text
冲突 C005 · function target()
原因：原位置 ours 修改，theirs 删除 [ENTITY_DELETE_MODIFY]

ours   : change-a @ a1b2c3d | old.ts::target() modified
theirs : change-b @ d4e5f6a | old.ts::target() deleted，new.ts::target() added
base   : 1122334 | old.ts::target()

ours 的文本变化（base → ours）：
-  return 1;
+  return 2;

疑似移动：old.ts::target() → new.ts::target()
匹配依据：base 中的源实体与 theirs 中的新增实体名称、类型相同，原始文本相同；
          本次分析范围内满足这些条件的新增实体有 1 个。

状态：old.ts 存在未解决冲突；new.ts 是关联的新增文件。
需人工处理：确认候选关系，选择或编辑最终位置与文本。
```

候选数由明确的筛选条件和本次分析范围计算，不代表已经证明语义身份。“原始文本相同”通过直接比较确认；若只有规范化后相同，须注明具体忽略项，不能称原始文本相同。已确定的源位置修改／删除与疑似移动关联分别展示，候选识别失败不改变原冲突。

“需人工处理”是固定提示，不动态推断移动目的或业务正确结果。若附加“检查调用方和导入”，必须标为通用检查建议；只有静态分析实际找到对应位置时才列出具体引用，不能暗示已完成跨文件正确性验证。

文件内可以保持原有三方正文，在标记行增加关联信息：

```text
<<<<<<< ours: change-a @ a1b2c3d | C005 function target() 已修改
export function target() {
  return 2;
}
||||||| base: 1122334 | old.ts::target()
export function target() {
  return 1;
}
=======
>>>>>>> theirs: change-b @ d4e5f6a | C005 原位置已删除；疑似移至 new.ts::target()
```

该片段只展示函数对应的冲突区域，实际文件仍保留区域之外的其他内容。theirs 在原位置没有函数，因此保持空侧；不能把 `new.ts` 的内容伪装成 `old.ts` 的 theirs 正文。

更丰富的报告可以并列展示“base 原函数、A 修改后函数、B 目标位置函数”，但必须标注各自路径和版本。这是跨文件对照，不是原文件标准 diff3 的三份输入。

## 3. 必须满足的行为与优先增强

- **必须冲突：** 修改与移动是同一实体的双方变化；纯移动、移动并重命名、移动并修改都不能因自动合并成功而绕过审核。覆盖跨文件移动，也覆盖同文件内可识别的实体位置或作用域移动。
- **区分移动与行号漂移：** 在函数前新增内容造成行号变化，不应被认定为函数移动。判断应结合路径、作用域和相对实体位置等证据。
- **尽可能关联目标：** 优先识别源侧删除与目标侧新增之间的关系。目标可以是新文件，也可以是既有文件中的新位置；不能只查新增文件。
- **提供证据与不确定性：** 可结合实体类型、名称、签名、作用域、函数体及变化前后的上下文进行匹配。移动并改名或改写只能在证据支持时关联；多个候选应列为候选，不强行选择一个。
- **区分复制与移动：** 原函数仍然存在时，目标新增可能是复制；同名同内容也可能是独立新增。不能仅凭相似度断言移动。
- **冲突不依赖识别成功：** 没找到可靠目标时，保留“修改与删除”冲突，并说明“未能可靠确定移动目标”。证据不足不能成为自动接受删除或合并的理由。
- **保持文件与实体关系：** 同一移动涉及的源、目标位置使用共同冲突编号；多个候选不应被误当作多个已确认移动。报告清楚区分真正未解决的文件与仅供关联检查的文件。
- **人工决定最终结果：** 不自动丢弃修改、不自动恢复旧定义、不自动覆盖目标函数，也不自动迁移修改或改写调用点。跨文件调用关系正确性仍需人工确认。

“智能”优先体现为基于可解释证据的关联和中文说明，不要求依赖大模型。冲突本身是硬性要求，移动识别是尽力提供的增强能力。

## 4. weave-core 与集成边界

单文件三方分析可以识别源文件中的修改／删除及目标文件中的新增，但不能仅凭源文件输入推导目标位置。需要在操作级别收集 base / ours / theirs 的跨文件变化，结合 weave-core 的实体分析和必要的解析、匹配接口，建立关联。

该能力不能假定 weave-core 的现有单文件入口已经直接提供。实体原文、作用域、范围及匹配证据的公开 API 限制见 [requirement.md 第 7 节](requirement.md#7-weave-core-能提供什么需要补充什么)。

新增需求：跨文件实体匹配还应提供独立的智能 diff，供人检视函数移动以及移动前后的实际修改，并与合并流程共用分析结果。Git 原生移动着色的能力边界、目标输出及实现分层见 [smart-diff.md](smart-diff.md)。

当前采用 `driver prepare` 显式读取三方快照，生成只读分析文件，原生 Git 调用 driver 时读取关联信息，见 [global-analysis.md](global-analysis.md)。不提供额外 Git 操作包装入口。

对于 Git 没有调用 driver、识别文件 rename 后直接合并成功等情况，预分析可提前报告已检测风险并返回 `1`；若仍继续 Git，结果文件不能迫使其产生 index conflict。将所有命中项呈现为可处理的未解决冲突仍是未完成目标，不能只扫描现有 marker。此边界与 [requirement.md 第 8 节](requirement.md#8-整个文件内容相同时的需求约束) 一致。

## 5. 后续实现的验收场景

| 场景 | 预期 |
| --- | --- |
| A 修改函数，B 原样移到新文件，Git 未识别 rename | 必须冲突；在证据支持时展示疑似目标位置及 A 的改动 |
| B 将函数移入既有文件 | 同样搜索该文件内的新增实体，不能因文件不是新增而遗漏 |
| B 移动并重命名／修改函数 | 必须保留冲突；匹配依据不足时不宣称已确认移动 |
| 整个文件被 rename，Git 自动合并了 A 的修改 | 预分析报告命中的风险；原生 Git 跳过 driver 时，自动转为未解决冲突尚未实现 |
| B 在同文件内调整实体位置或作用域，A 修改该实体 | 可识别为真实移动时必须冲突；普通行号漂移不按移动处理 |
| 多个目标函数与源函数相似 | 保留冲突，列出候选及依据，不自动选定目标 |
| B 复制函数但保留原定义 | 不误报为已确认移动；是否存在其他冲突按严格规则独立判定 |
| 未能确定移动目标 | 保留源位置的修改／删除冲突，报告识别限制 |

验收应通过真实 Git 操作检查冲突状态、源与目标内容及报告关联，确认没有静默丢失修改、重复定义或错误迁移。本文示例中错误处理可能造成这些问题，并不意味着工具能够证明所有解析后的代码都不存在这些问题。
