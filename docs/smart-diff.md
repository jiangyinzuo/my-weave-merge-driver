# 智能实体 diff：移动识别与人工检视需求

本项目需要将用于合并的实体分析能力延伸为独立的智能 diff，供人检视函数移动及移动前后的实际修改。本文保留为需求草案。当前决定暂不实现或暴露 diff 命令；先实现 driver 和显式三方预分析，见 [global-analysis.md](global-analysis.md)。

## 1. Git 自带能力与边界

Git 已经能辅助观察移动代码。例如对两个提交执行：

```sh
git diff --color=always --color-moved=dimmed-zebra --color-moved-ws=allow-indentation-change OLD NEW
```

`OLD`、`NEW` 是待替换的提交或树引用。默认建议在终端交互使用颜色；这里显式启用颜色是为了说明移动着色效果。

| 能力 | 能提供什么 | 不能保证什么 |
| --- | --- | --- |
| `--color-moved` | 对当前 diff 中不同位置的匹配增删文本着色，包括跨文件的移动文本 | 不建立可靠的函数身份，不提供函数级来源／目标关联报告；移动并修改时可能只匹配部分文本 |
| `--color-moved-ws=allow-indentation-change` | 辅助识别整体缩进变化后的移动代码块 | 不等于忽略任意语法或业务变化 |
| `-M` / `-C` | 检测文件级重命名／复制 | 不负责把一个文件中的函数关联到另一个文件中的函数 |
| `-W` / `--function-context` | 按语言的函数边界模式扩展上下文 | 不是跨文件实体匹配，也不保证理解所有语言结构 |
| `--histogram` / `--patience` | 改善部分重排场景下的文本匹配与可读性 | 不直接生成函数移动的结构化关系 |

上述说明依据本次环境中的 Git 2.53.0 帮助与手册。移动着色是文本启发式：例如 blocks、zebra 系列模式对匹配块有长度要求，小函数、常见模板代码和移动后的修改都可能影响结果。路径过滤也会限制可见的源、目标；默认工作区 diff 不包含普通未跟踪文件，因此未加入比较范围的新文件不会被用来关联移动。

可以修改 Git 源码加入更多实体分析，但这会涉及语言解析、跨文件匹配和 Git 版本维护。建议先使用 Git 获取版本与文本差异，在本项目中实现不足的实体分析能力，通过独立命令提供完整报告。

Git 的 external diff、textconv 可以扩展展示，但通常按文件或文件对调用，缺少天然的全仓库实体上下文。它们可以作为后续集成入口，不应成为跨文件匹配的唯一实现方式。修改 diff 的显示方式本身也不会改变 Git merge 的冲突判定。

## 2. 确定的产品需求

**未来考虑提供可独立运行的智能 diff，与 merge driver 共用实体分析能力；具体接口尚未确定。** 原生 Git 的文本检测难以满足函数级关联时，由本项目补充实现，复用 weave-core／sem-core 可用能力；现有公开接口不足时需补充接口或适配层。

- 展示实体新增、删除、修改、重命名、移动，以及移动并修改；在证据支持时关联旧、新位置。
- 同时覆盖跨文件移动和同文件内真实的位置／作用域变化，区分普通行号漂移。
- 将“位置变化”和“实体内容变化”分开呈现，使人不必自行对照两大段删除与新增来寻找几行实际修改。
- 区分移动、复制、独立新增与匹配不确定；多个候选不能静默配成唯一关系。
- 输出中文摘要、路径、两侧版本与范围、匹配依据，并允许展开完整实体和原始文本 diff。
- 归并为移动摘要后，仍须保留可访问的原始增删内容；不能隐藏未匹配文本、注释、导入或其他非实体变化。
- 明确标注不支持的语言、解析失败、分析范围受限等情况，并保留行级 diff；不得把“没有识别到移动”表述为“没有移动”。

智能 diff 是人工检视报告，不应默认宣称可供 `git apply` 使用。标准补丁另由原始文本 diff 提供；匹配时忽略格式等操作也不能丢掉实际的格式变化。

## 3. 目标输出示例

假设旧版本的 `old.ts::target()` 返回 `1`，新版本将它移到 `new.ts`，并将返回值改为 `2`。以下展示只在匹配证据足够时使用；短小、同质函数尤其需要保留歧义说明。

```text
疑似移动并修改 · function target()
旧版本 OLD：old.ts:1
新版本 NEW：new.ts:1

候选关联：old.ts::target() → new.ts::target()
匹配依据：源位置 deleted，目标位置 added；类型、名称和声明行相同；
          本次范围内同类型、同名的新增实体有 1 个。

候选文本对比：
 export function target() {
-  return 1;
+  return 2;
 }

可展开：旧实体全文、新实体全文、两文件的原始文本 diff。
```

名称、类型来自解析，声明行和正文来自原文，候选数来自指定范围内的明确筛选规则。该示例不使用未定义的“结构相近”评分，也不声称已经证明移动关系。后续若加入 token／AST 相似度，必须定义算法和阈值并展示实际证据；相似度分数不是匹配正确率。

候选实体原始文本完全相同时可以显示“候选文本相同，路径／位置不同”；如果只在忽略格式后相同，应说明忽略项，并保留实际文本差异。这不等于语义等价：模块作用域、导入、闭包和初始化顺序变化仍可能影响行为。

## 4. 与严格合并共用分析逻辑

建议把实现分为：版本和文件采集、实体解析与跨文件匹配、展示或冲突判定。智能 diff 使用两份快照；合并分析分别比较 base → ours、base → theirs，并通过 base 实体和匹配证据关联双方变化，处理新增实体及歧义。

同一套分析结果可以服务于：

- 两版本智能 diff：说明函数从哪里到哪里，以及修改了什么。
- 三方合并预览：说明一方修改、另一方移动，以及两者为何需要共同审核。
- 严格冲突生成：保留必须人工处理的状态，关联源、目标位置。

匹配与策略需要分离。对两版本 diff 来说，识别出移动只是描述变化；对三方合并来说，识别出一方修改、另一方移动仍必须冲突，不能把智能识别当作自动合并授权。详见 [modify-vs-move.md](modify-vs-move.md)。

不应只解析 `--color-moved` 的 ANSI 颜色来生成实体关系，也不能仅比较两侧分支最终文件而丢失 base 的身份依据。

## 5. 命令与范围规划

首个独立入口建议支持两个明确提交／树的仓库级比较，例如 `工具名 diff OLD NEW`；命令名称暂未确定。后续扩展暂存区、工作区和三方预览时，须明确每种模式的输入与未跟踪文件策略。

跨文件匹配先确定分析范围，再做结果过滤。若只分析指定路径，应注明可能遗漏范围外的移动目标；不能展示为完整仓库结论。结果不确定时保留候选列表和原始 diff，禁止依赖不稳定的遍历顺序强行匹配。

验收应覆盖跨文件纯移动、移动并修改、移动并改名、移入既有文件、复制、同名函数歧义、普通行号漂移及解析降级，并验证报告与合并使用的实体关系一致、原始变化没有遗漏。

## 6. 函数重命名的分析边界

Tree-sitter 提取语法实体，本身不维护跨版本身份。当前固定版本的 weave-core 另有实体匹配层，支持 `Renamed` / `RenameEdited` 分类，使用名称归一化后的文本、文本相似度及调用点变化等证据。实现见 [v2/match_phase.rs](https://github.com/Ataraxy-Labs/weave/blob/a3f501d19601126fefcc40a3ebb764b8d07d39fc/crates/weave-core/src/v2/match_phase.rs)。

例如 `parse()` 改名为 `decode()` 且正文不变，可形成较强的重命名候选；多个相似函数、重命名同时大幅修改正文时可能误配或漏配。确定性的算法不等于匹配一定正确。提示须附依据并保留不确定性，不能据此取消应有冲突。当前全局预分析只关联同名同原文的跨文件移动，尚未接入这些重命名候选。
